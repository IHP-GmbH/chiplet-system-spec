# Version policy

One rule for every versioned artifact published from this repository: the
`.chiplet` `format_version` and each governed sidecar (`io_pads.json`,
`pins.json`, the black-box padmap, the boundary manifest,
`interconnect_methods.json`).

## The rule

A version is a **quoted** `MAJOR.MINOR` or `MAJOR.MINOR.PATCH` string. Given a
consumer that supports `MAJOR.MINOR`:

| Declared | Verdict |
|----------|---------|
| Same major, minor at or below supported | accept |
| Same major, higher minor | accept, and warn (see the channel note below) |
| Different major (higher or lower) | refuse |
| Missing or malformed | refuse |

`PATCH` is parsed and then ignored; it never changes a verdict.

Accepting a higher minor is what makes the format additive: a consumer reads the
document as the version it supports and ignores what it does not recognize, and
the warning is there so an unexplained missing field has somewhere to point.

**The warning channel, stated so no host is surprised.** The reference readers deliver the
same-major-higher-minor event two ways: through Python's `warnings` channel (category
`ContractVersionWarning`, or its `.chiplet` subclass `FormatVersionWarning`, deduplicated per
artifact and version) for a human to see, and, when the caller passes `on_warn`, to that hook,
every event, undeduplicated. The `warnings` channel is a process-global the HOST configures. A
host that escalates warnings to errors (`python -W error`, `filterwarnings("error")`, a test
runner set strict) will therefore REFUSE a compatible higher minor, and it does so by its own
choice, not by this policy. A consumer that needs policy-conformant acceptance under such a
host filters the category around the call or takes the event through `on_warn`, which never
escalates. The C++ reader has no global channel and returns the verdict; a C++ host decides.
This is the same statement as the rest of the policy: what is accepted is decided here, how
loudly is decided by the host, and the two must not be confused.
Refusing a *lower* major matters as much as refusing a higher one: an older major
is a different document shape, and half-parsing it is worse than not reading it.

Quoting is part of the rule, not a style preference. Unquoted `1.10` is `1.1`
under PyYAML and `1.10` under yaml-cpp, and in JSON it is the number `1.1` with
no way back.

The reference implementation is
`chiplet_format_io.check_contract_version(value, supported, name=...)`, where
`supported` is one `"MAJOR.MINOR"` string or a sequence of them (see [Changing
the major](#changing-the-major)), with `check_format_version` as the
`.chiplet`-specific entry point, reading the module's `ACCEPTED_FORMAT_VERSIONS`.
Each entry of that set is the highest minor implemented for its major.
`SUPPORTED_FORMAT_VERSION` is the version writers stamp on an assembly and
`SOURCE_FORMAT_VERSION` the one they stamp on a source (see [Stamps per document
kind](#stamps-per-document-kind)); each must be at or below the set's entry for
its major, because a writer that stamps what its own reader refuses or warns on
is a policy nobody can follow. The C++ mirror carries the same constants
(`ACCEPTED_FORMAT_VERSIONS`, checked by a `static_assert`) and the same verdicts, and both run the shared
verdict oracle `conformance/fixtures/version_policy_cases.json`. One difference,
inherited rather than chosen: a `.chiplet` `format_version` is `MAJOR.MINOR` only
(no patch component), and `schemas/chiplet.schema.json` pins it that way; the
sidecars accept the patch component because emitters already write `"1.0.0"`.

## What bumps what

- **MINOR** for anything additive, *and for any change to the meaning of an
  existing key*. A key that silently starts meaning something else is the one
  change a consumer cannot detect, so it never happens under an unchanged
  version. If old and new readings of the same bytes can disagree, it is at least
  a minor.
- **MAJOR** for a change that makes an old consumer wrong rather than incomplete:
  removing a key, changing a type, changing a coordinate frame or a unit.
- **PATCH** for anything a consumer cannot observe: wording, examples,
  a description in a schema.

The dividing line, stated once because every future argument is a version of it:
a MINOR only adds what a consumer can ignore and remain correct, and whatever a
consumer must honour to stay correct is a MAJOR. It is a question about the
CHANGE, not about the diff. A new optional key a reader may skip is a minor; the
same key is a major the moment skipping it makes the reader wrong rather than
incomplete, and a new value in a closed vocabulary is a minor because a consumer
that does not know the value can refuse the ELEMENT that carries it and report
it, ending up incomplete rather than wrong.

That subordinate clause has to say ELEMENT. Refusing the whole DOCUMENT does not
qualify under the sentence above it: a consumer that cannot open the file has
not ignored the value and remained correct, so if refusing the document were the
reason, every added enum member would be a MAJOR by this policy's own test. The
justification would eat the criterion two lines above it. This is also why the
mark on an unrecognised member is structural rather than a matter of taste: the
element-level refusal is what makes the MINOR label true, so a consumer that
refuses documents instead of elements is not being strict, it is turning a
MINOR into a MAJOR for everyone downstream.

Which leaves one line to draw, because this specification does land
document-level refusals and calls them MINOR (SPEC-14's repeated top-level key,
SPEC-36's forbidden line breaks) while SPEC-32 leans on the paragraph above to
forbid one. They are reconcilable, and the reconciling sentence is this: a
DOCUMENT-level refusal is permitted only for bytes that have NO conforming
reading at all, and every refusal grounded in a VALUE a reader does not
recognise is ELEMENT-level. The test is not how serious the defect looks, it is
whether a conforming reading exists. A repeated top-level key has none (PyYAML
keeps the last value, yaml-cpp the first, and nothing downstream can tell); a
forbidden line break has none (a parser breaks a line where the grammar does
not, so the two build different documents); an unrecognised member of a closed
vocabulary has one, so a reader that cannot use it is incomplete, must say so,
and must carry on. That makes SPEC-14, SPEC-32 and SPEC-36 one rule rather than
three precedents, and it is the sentence to quote the next time this argument
comes up.

The sentence speaks about a value a MINOR added, so it binds a reader reading a
document stamped ABOVE the minor it implements. A value unknown in a document
stamped at a minor the reader fully implements is out of contract (the
`solder_bump` row below: no producer may emit a value before the minor that
adds it), so no conforming reading is owed at that minor and a reader may
refuse the document. It may also read it element by element, as the `.chiplet`
readers do for `interfaces[].type` since 1.2.0; what it may not do is refuse
the document for a value a higher minor stamp carries.

That prohibition is executable from the document alone. Each member added after
1.0 carries the minor that added it as schema data (`x-since` beside its enum in
`schemas/chiplet.schema.json`), both reference validators read the same map
(`MEMBER_SINCE`, `kMemberSince`, held to the schema by
`conformance/test_member_since.py`), and the verdicts are: a document stamped
below a member's minor is refused, whether or not the reader knows the member;
at or above it, the clauses above apply unchanged. A reader's own vintage never
decides the verdict, only the document's stamp does. Writers read the map too:
no writer stamps below the highest minor among the members it writes, which is
the one case where a lossy writer, which otherwise stamps
`SUPPORTED_FORMAT_VERSION`, stamps higher. The retrofit is empty: absent means
1.0, and only members added from 1.1 on carry a tag.

## Stamps per document kind

From format 1.1 a `.chiplet` is one of two kinds, and each has its own stamp.
An **assembly** is what every reader has always read; its writers stamp
`SUPPORTED_FORMAT_VERSION`, still `"1.0"`, because nothing an assembly carries
needs more. A **source** (a top-level `system` block) did not exist before 1.1,
so its writers stamp `SOURCE_FORMAT_VERSION`, `"1.1"`. The rule behind both is
one rule: a writer stamps the lowest minor its content needs, never the highest
minor its reader implements, so a document only claims a minor when it carries
something of it, and a consumer at 1.0 keeps reading every assembly without a
warning. A passthrough writer still preserves a higher stamp it was handed.

Why `system` is a MINOR and not a MAJOR: it is a new root key, and no assembly
gains or loses a meaning. A 1.0 reader handed a source warns on the minor and
refuses it by the `_metadata.finalize_required` guard a source always carries;
the hole is a caller that allows intermediate files, which a 1.1 reader closes
by refusing every source on its assembly path, whatever it is told
(`SourceDocumentError`). The source is the only document kind such a reader
refuses at the document level, and it qualifies under [What bumps
what](#what-bumps-what): a source has no conforming reading AS AN ASSEMBLY, so an
assembly reader that read one would be wrong, not incomplete.

Format 1.3, the unplaced source, is a MINOR by the same test, though it relaxes
requirements rather than adding a key: a die may omit `at`, the carrier `size`,
`external` its `edges`, `system.dies` may be absent, and the root key `unplaced`
holds the external entries no edge carries yet. A source reader before 1.3 handed
such a file warns on the minor and refuses it, for the missing required key or
for `unplaced`, an unknown ROOT key, which a source reader refuses at any minor.
That is why `unplaced` is a root key: as an item or `system` key of a higher
minor it would be skipped with a note, and the reader would read on without
those externals, wrong rather than incomplete. A file stamped below 1.3 that
leaves anything unplaced is refused naming 1.3, and a writer stamps `"1.3"` only
while something is unplaced, so a placed source keeps the stamp it had.

Format 1.4, a die's admission, is a MINOR by the same test, and the reason it
is an item key is the reverse of 1.3's. A source reader before 1.4 skips
`dies[].admission` with a note and reads on with the die not admitted; a
consumer that places a die it did not build only on an admission then refuses
that die. The skip fails closed, so the reading is incomplete, never wrong.

Format 1.5, a rail's routing requirement (`rails[].width_um`, or `amps` with
`current_density_ma_per_um`), is a MINOR by the same test, and it is the hard
case. A source reader before 1.5 skips the three keys with a note and reads on,
and a router fed that reading draws the rail at the layer minimum: wrong, not
incomplete, the reason 1.3 made `unplaced` a root key. They stay item keys
because the rail is the one place a requirement belongs, and a root key would
restate every rail name in a second place that can drift from the first. The
fail-closed moves to the consumer: a flow that routes from a source checks that
the readers it uses carry the three keys in `SOURCE_KEY_SINCE`, and refuses a
reading that skipped any `system.rails[]` key, before it builds anything. A
consumer that does not route reads the skip as incomplete.

The connectivity form (`chiplet_system.connectivity`, the schematic front
end's output, read by `chiplet_system_description.connectivity`) follows the
same rule. Each sheet kind is written at the lowest minor its content needs: a
generated sheet at 1.0, a blank one at 1.1, a classic one at 1.3, the minor
that adds each classic symbol's `units` and `jumpers` (gds_to_kicad writes
them for the board interposer-pnr draws against the sheet). The reader is at
1.3 and reads neither key, so a classic form reads the same at 1.2 and 1.3,
and no writer in the ecosystem draws the newer-minor warning from it.

## Changing the major

A MAJOR bump is the change that makes an old consumer wrong rather than
incomplete, so it cannot ship the way a MINOR does. On the day a producer
switches, every consumer that has not switched refuses the document. The refusal
is correct; the flag day it creates is not necessary, and this section removes
the flag day without weakening the refusal.

**1. A consumer declares the SET of majors it accepts.** One `MAJOR.MINOR` entry
per major, carrying the minor that consumer was written for. The single-string
form is the one-element set, with exactly the verdicts it always had, so nothing
changes for a consumer that accepts one major. Two entries with the same major
are a PROGRAMMING error rather than a data error: two floors for one major have
no verdict between them. They are refused at call time (`ValueError` in Python,
`std::invalid_argument` in C++), not at read time on whatever document happens to
arrive first, so the mistake surfaces on the consumer's first call. An empty set
is refused the same way: a consumer that accepts nothing can read nothing, and
silently refusing every document would read as bad data.

**2. The verdict.** Pick the entry whose major equals the declared major.

| Declared, against the accepted set | Verdict |
|---|---|
| No entry with that major (higher or lower) | refuse, naming EVERY accepted major |
| Minor at or below that entry's minor | accept |
| Same major, higher minor | accept, and warn (the channel note above) |
| Missing or malformed | refuse |

Naming every accepted major is the part that is easy to get wrong: a refusal
that names one major while the consumer accepts two sends the producer to fix
the wrong end of the window. `PATCH` is still parsed and ignored, on the declared
version and on the entries alike, so `1.0` and `1.0.0` are the same floor.

**3. The bump, in three steps, each shippable on its own.**

1. Consumers add the new major to their set while producers still emit the old
   one. A consumer may add a major only when the code path for that major exists:
   "accept" is a statement about the reader, never an intention.
2. Producers switch to the new major. Both majors are now in the field, every
   updated consumer reads both, and the conformance corpus carries a document of
   each major for as long as the window is open.
3. Once every governed producer emits the new major, consumers drop the old
   entry and the corpus drops the old document.

The window has to be finite, and step 3 is what makes it so. A set that only
grows is a reader that still understands every shape the format ever had, which
is the state a major bump exists to leave.

## Deprecating a key

Announce it, keep it working for at least one minor, then remove it in the next
major. Concretely: bump MINOR when the replacement lands, keep emitting and
reading the old key for that minor with the schema description naming it
deprecated and naming the replacement, and only then stop. A key that disappears
in the same release that announces it is a major change wearing a minor's label.

The one deprecation currently in flight is `pins.json`, whose existing producers
write the bare integer `1` where the rule wants the string `"1.0"`. The schema
accepts both for now and names the integer deprecated; a consumer normalizes `1`
to `"1.0"` before applying the rule, and that normalization is the only place the
legacy spelling is understood. `check_contract_version` refuses a bare number,
because JSON cannot tell `1.0` from `1` and neither can the reader.

## Byte identity of vendored copies is a tripwire, not the contract

Several of these artifacts are vendored: the reference reader is copied into
consuming tools, and schemas are mirrored next to the code that reads them. It is
useful to notice when a copy has drifted, and a byte-comparison in CI is a fine
way to notice it.

It is not the compatibility contract. A copy that differs by a comment is
compatible; a copy that is byte-identical to an artifact whose *meaning* changed
is not. Consumers gate on the declared version through the rule above, never on
a hash of a vendored file. Where the vendored artifact is the reader itself,
`chiplet_format_io.__version__` is the value the copy carries for exactly this
purpose, so a consumer can require a reader release without comparing bytes. It
is the release of the reader, not of the format: `SUPPORTED_FORMAT_VERSION`
still says which documents that reader understands.

The C++ reference carries the same number in `READER_RELEASE`, so a vendored C++
copy is gateable the same way and neither reference can move alone: a
conformance test reads the constant out of the header, the version out of the
C++ package metadata, and `__version__` out of the module, and fails if the
three disagree.

The technology package manifest (`libs.tech/adk/technology.json`, schema
`technology_package.schema.json`, read by `chiplet_format_io.technology_package`)
starts at `"1.0"` and follows the same rule. Its reader refuses another major, and
at a higher minor of `1.0` it ignores and reports each unknown top-level member
before the schema check, so a later minor may add a member and an older reader
still judges the sets it knows. A key added inside an existing member needs the
reader's next minor, because those objects are closed. The routing descriptors a
package names keep their own version, interposer-pnr's: the manifest states the
range it accepts, and a descriptor outside it fails set A rather than refusing
the package.

"a\Lb"` on one line, `: x: 1` on the next) and a key carrying a space came out bare as `a b:`; in both, the split reported two top-level keys, `loads` reported three, and the extra block was attributed to `assembly`, whose owner drops it on the next re-export. That is the SPEC-36 property (split and parse disagree) produced by our own writer, so `dumps()` now splits the text it just emitted and refuses when the split does not return exactly the keys it was given, in order. MINOR and not PATCH because a consumer can OBSERVE both refusals: the splitting accessors (`top_level_blocks`, `top_level_block`, and the C++ `flow_source`) refuse documents they used to split, and `dumps()` refuses mappings it used to write. Two of those moved verdicts are in the shared oracle and are named there rather than left to be discovered: `flow :` and a whole document in flow style are now not splittable, not merely undelimitable. Not a format change: no legal document's BYTES or MEANING moved, reading is unchanged in both readers, and the sequence-entry exemption is what keeps that true (PyYAML writes a block sequence at the parent's indentation, so 68 of the 70 column-zero non-key lines across the 77 tracked `.chiplet` in this ecosystem are `- id: ...` entries under `components:`, and a rule without the exemption would refuse to split almost everything we ship). The writer-output digest did NOT move, and that is asserted rather than claimed: `conformance/fixtures/writer_output_pin.json` names release 1.4.0 with the unchanged sha256 from 1.3.0. At that matching release, `conformance/test_writer_output_pin.py` rejects any changed byte; a one-byte perturbation is the negative control. The C++ check includes caller-supplied flow source rather than assuming all column-zero keys originate in its fixed mapping. |
| 1.3.0 | The Python writer stopped spelling U+0085 as `\N` and now writes `\x85`. Measured on PyYAML 6.0.3 and yaml-cpp 0.8.0: `"a\Nb"` reads back as `61 c2 85 62` in Python and `61 85 62` in C++, a bare 0x85 that is not valid UTF-8 on its own, so a document this project's Python writer produced handed this project's C++ reader a malformed string. `\L` and `\P` round-trip identically in both and are unchanged; the defect was one escape, not the family. A MINOR and not a PATCH because a consumer CAN observe it: the bytes our writer emits for such a value changed, and at least one consumer runs a byte-exact writer parity gate. Reading is unaffected in both directions, since both spellings decode to U+0085 in both readers, so nothing on disk becomes illegal and no document's meaning moves. THE REASON THIS ROW EXISTS AT ALL is a process defect worth naming: the change landed first with the release left at 1.2.0, so two legitimate vendored copies, one from each commit, declared the same release over different bytes. The ecosystem's contract registry treats exactly that as DRIFTED, precisely so an in-place edit cannot be invisible, and a CONSUMER caught it during a re-vendor rather than this repository catching it on the way out. The rule the miss implies: when the declared artifact's bytes move, the declared version moves with them, and the deliberate no-bump of the SPEC-21 row above is the narrow exception, allowed only because nothing a consumer can observe moved with it. |
| 1.2.0 | The readers stopped refusing an unrecognised `interfaces[].type` (SPEC-32, panel ruling Q1): they carry the string, report it through `on_warn` at parse, and refuse nothing over it. ## Unversioned corrections since 1.0

Two passes over the history, and this table is the result of the second.

**Pass one, declared bumps.** No governed artifact in `schemas/` or `docs/` has
declared a MINOR or MAJOR bump since 1.0: every row of the spec's own Version
History is still `1.0`, and the sidecars still declare `"1.0"`. Nothing to
reconcile.

**Pass two, shape changes that landed without a version change.** Every one of
them is judged under one sentence, the one in [What bumps what](#what-bumps-what):
a MINOR only adds what a consumer can ignore and remain correct, and whatever a
consumer must honour to stay correct is a MAJOR. A row that cannot be justified
under it is written down as such rather than argued into shape.
